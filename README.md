# MelKit

**مدير محتوى Melon Sandbox — نسخ احتياطي، مشاركة، تنظيم، ومجموعات مودات.**  
**Melon Sandbox content manager — backup, transfer, organization, and mod profiles.**

| القرار | القيمة المعتمدة |
| --- | --- |
| اسم التطبيق | **MelKit** |
| Application ID / namespace | `com.spinel.melkit` |
| المنصة الأساسية للاختبار | Android 16؛ الحد الأدنى Android 7 / API 24 لتوافق Shizuku 13.1.5 |
| اللغات | العربية RTL والإنجليزية LTR، مع اختيار اللغة من الإعدادات |
| المظهر | داكن افتراضيًا، بطاقات واضحة ولمسات خضراء وفق التصميم المعتمد |
| مصدر الكود الرئيسي | https://github.com/ibrmsaed87-cell/MelKit |
| مستودع GitLab | https://gitlab.com/spinel-group/melkit |
| جهة البناء | GitLab CI؛ GitHub يقوم بالمزامنة فقط |
| الحزمة الأولى على الهاتف | APK بإصدار Release ومفتاح التوقيع الثابت |

> هذا الملف هو خريطة المشروع ومرجع القرارات. تُحدّث حالة المرحلة وأدلة اختبارها في كل تعديل مرتبط بها. وجود ميزة في الخطة لا يعني أنها نُفذت أو اختُبرت.

## الحالة الحالية

**تعديل واجهة الإشعارات بعد مراجعة الهاتف:** طلب المستخدم إزالة بطاقة «تحديثات التطبيقات» والاكتفاء بسؤال النظام عند أول فتح. أُزيلت البطاقة، وبقي طلب الإذن مرة واحدة على Android 13 فأحدث مع تسجيل أول فتح حتى عند وجود الإذن مسبقًا. لا تطلب المشاركة إذن الإشعارات مرة أخرى. التعديل محفوظ على فرع العمل للبناء القادم؛ استقبال FCM وفتح رابط المتجر عند الضغط مستمران في الكود.

**نتيجة اختبار الإشعارات وتطبيقاتنا:** أكد المستخدم نجاح وصول الإشعار وفتح رابطه. طلب بعدها عرض أيقونات التطبيقات بدل الرموز العامة، وتفعيل رابط MMKB المتوقع من البكج `com.spinel.mcbk`. أُضيفت الأيقونات الأصلية كموارد مضمّنة، وفُعّل زر المتجر؛ إتاحة صفحة MMKB للعامة لم تُتحقق. هذه التعديلات مع إزالة بطاقة الإشعارات على فرع `codex/melkit-phone-review-20261109` للبناء القادم. [المصادر والتحقق](docs/PROMO_APPS.md).

**جولة الإشعارات — 9 نوفمبر 2026:** أذن المستخدم بربط Firebase ثم إنشاء نسخة اختبار تجمع الإشعارات والملاحظات الأربع. أُدمج عميل `com.spinel.melkit` من الملف المرفوع، وأضيف FCM وقناة/topic خاصان بالتطبيق وطلب الإذن وحالته في الإعدادات. تحمل الرسالة المفتاح `url` لرابط تطبيق على Google Play؛ يُتحقق منه ولا يُفتح إلا عند الضغط على الإشعار، في مساري المقدمة والخلفية. اجتاز الكود 422 فحص مضيف وفحص XML والترجمات والصياغة؛ البناء وتجربة الوصول الفعلي والضغط تنتظران نتيجة GitLab والهاتف. [إعداد الإشعارات واختبارها](docs/FCM_SETUP.md).

## فائدة التطبيق وحدوده

يساعد اللاعب على حماية المحتوى الموجود داخل اللعبة، نقله إلى هاتف آخر، وتنظيم ما يريد تفعيله. يشمل المودات والخرائط وملفات الحفظ، والعوالم بعد إثبات دعم ملفاتها.

**MMIX** يستورد ملفات اللعبة المحمّلة من الخارج، بما فيها ZIP والاستيراد المتعدد. **MelKit** يدير المحتوى الموجود والنسخ والحزم الخاصة به. استعادة نسخة MelKit واستقبال محتوى من هاتف آخر جزء من MelKit؛ لا نكرر مستورد التنزيلات العام.

لا يشمل النطاق نقل ملكية مشتريات المتجر أو العملات أو الحسابات، ولا استرجاع ملفات حُذفت قبل وجود نسخة منها. لا نعد بإصلاح كل انهيار أو بضمان 60 FPS.

### قواعد سلامة الملفات

1. نسخ الملفات الفردية تُجمع في موقع مشترك اعتمده المستخدم: `Download/MelKit`، مع مجلدات `Mods` و`Maps` و`Saves` و`Worlds` حسب أصل الملف، والمجلدات الداخلية إن وجدت. يُنشأ كل مجلد عند الحاجة، وتبقى النسخ بعد إزالة MelKit. اختيار مواقع الخزنة والعزل في مراحلها اللاحقة، خارج مساحة التطبيق التي يمسحها Android عند إزالته.
2. تجري عمليات تغيير ملفات اللعبة بعد إغلاق اللعبة. نفحص القراءة والكتابة فعليًا ولا نعتبر منح الإذن وحده نجاحًا.
3. كل نقل يبدأ بنسخ موثّق ثم التحقق من الحجم وبصمة المحتوى قبل إزالة المصدر، مع سجل قابل لاستكمال العملية أو التراجع عنها.
4. خطأ الصلاحيات أو صيغة غير مدعومة يعرض **تعذر الفحص**، ولا يصنّف الملف تالفًا. الملف الفارغ ليس إثباتًا لسبب انهيار اللعبة.
5. يُفحص فراغ التخزين، وتبقى التغييرات قابلة للمراجعة. قد يحتاج الحفظ مودات معينة؛ لا نحذف المكررات تلقائيًا لمجرد تطابق المحتوى.
6. لا نغيّر معرّفات المودات أو مراجع الحفظ. تجربة تعديل التصنيف والصورة تكون على نسخة وبأدلة من داخل اللعبة.

## UI / UX واللغات

- التصميم المعتمد: شاشة رئيسية داكنة، ملخص المكتبة، بطاقات النسخ والنقل والمجموعات والفحص، المجموعة الحالية، وآخر نسخة.
- الشريط السفلي: الرئيسية، المكتبة، النسخ، المشاركة، الأدوات. يضم قسم الأدوات تبويبين واضحين: **الأدوات** و**المزيد من التطبيقات**، للحفاظ على خمسة عناصر في الشريط السفلي؛ تبويب التطبيقات يحوي البطاقات الأربع المطلوبة.
- تتضمن الأدوات التصنيفات والصور المصغرة وسجل العمليات. لا نحشر كل الأدوات في الشاشة الرئيسية.
- بطاقات ملفات المكتبة تعرض صورتها المضمّنة متى كانت الصيغة مدعومة، في إطار مربع بحواف دائرية بجانب الاسم. تحافظ الصورة على نسبتها ومظهر البكسل، وتبقى أيقونة النوع عند غياب الصورة. هذه قراءة معاينة فقط؛ اختيار صورة من المعرض أو تعديل صور اللعبة يتبع مراحله اللاحقة.
- تبويب «النسخ» يعرض أيضًا الصورة المصغرة للملف المحفوظ بجانب اسمه، مع حجمه ومكانه وزر «استعادة إلى اللعبة». تُعرض حالات الفراغ والقراءة والإذن بوضوح. لا تعرض رسالة الحفظ بصمة SHA للمستخدم؛ التحقق يظل داخليًا.
- كل نص مرئي في موارد ترجمة عربية وإنجليزية. تُراجع الأرقام والأحجام والتواريخ واتجاه RTL/LTR.
- في أول تشغيل تتبع اللغة العربية لغة الجهاز العربية، والإنجليزية لبقية اللغات، مع تبديل يدوي محفوظ.
- لا نعرض بيانات وهمية في APK التجربة على أنها محتوى حقيقي؛ بيانات التصميم أمثلة فقط.
- الوصول غير المتاح يظهر رسالة مفهومة وخطوة إصلاح. مسار Shizuku يُختبر قبل اعتماده، مع دليل عربي وإنجليزي عند الحاجة.
- شاشة الاقتران والكاميرا لا تفرض الوضع الأفقي. بدء نقل جديد يمسح حالة الجلسة السابقة.

### بطاقة شرح Shizuku

- أُضيفت بطاقة واضحة بعنوان **شرح إعداد Shizuku** أعلى قسم الأدوات، على غرار دليل تطبيق Minecraft Backup الذي أشار إليه المستخدم باسم MMBK. يبدأ الدليل ببطاقة مشاهدة الفيديو ثم خطوات الإعداد النصية ورابط التنزيل الرسمي.
- تعرض البطاقة فيديو عربيًا عندما تكون لغة MelKit عربية، وفيديو إنجليزيًا عند اختيار الإنجليزية، بتنسيق منسجم مع بقية الواجهة.
- يوضح الشرح الإعداد لأول مرة: فتح Shizuku، إعداد التصحيح اللاسلكي والاقتران، إدخال رمز الاقتران في إشعار Shizuku، ثم بدء الخدمة ومنح MelKit الإذن.
- يبدأ الفيديو بالتنويه إلى أن الإعداد والاقتران خطوات أول تشغيل؛ في الاستخدام المعتاد لاحقًا يكفي فتح Shizuku وبدء الخدمة، مع توضيح ما يلزم إن طلب النظام إعادة الاقتران.
- تتضمن البطاقة رابط تنزيل Shizuku الرسمي. وتوفر رسالة «يجب تشغيل Shizuku أولًا» اختصارًا لفتح بطاقة الشرح.
- الفيديوهان مضمنان في `res/raw` بحجم إجمالي 5,082,738 بايت. يختار المشغّل المورد العربي أو الإنجليزي صراحةً من لغة التطبيق، دون الاعتماد على لغة الهاتف أو مشغّل خارجي.
- معيار القبول: ظهور الفيديو المناسب للغة، وضوح الاقتران والإشعار، وإمكانية الوصول إلى الشرح من الأدوات ورسالة الحاجة إلى Shizuku. أكد المستخدم في 9 نوفمبر تشغيل كل فيديو في لغة واجهته على النسخة المثبتة؛ لا يوجد فحص كامل للتشغيل دون إنترنت أو لآخر تعديلات الواجهة الأربعة بعد.

### قرارات واجهة التحكم — 4 نوفمبر 2026

- أداة المودات: الفعّالة هي التبويب الافتراضي، والمعطّلة تبويب مستقل، ويظهر العدد بجانب كل عنوان. التصفية على كامل القائمة قبل تقسيمها إلى صفحات؛ لا ننقل المستخدم إلى التبويب الآخر بعد التعطيل أو الإعادة.

### قاعدة تحديث الخطة

كل تعديل يذكر المشكلة، المرحلة، التغيير، التحقق، والحدود المتبقية. قبل إنهاء المرحلة تُحدّث هذه الصفحة بأدلة: commit، رابط pipeline، إصدار التطبيق، الهاتف/المحاكي، ونتيجة الاختبار. لا توضع علامة نجاح لمجرد اكتمال الكود أو تجميع APK.

## GitHub → GitLab → APK

1. ننشئ مستودع GitHub، ثم نرفع **README.md وحده كأول commit**.
2. نرفع ملفات التأسيس والربط في commit لاحق. الفرع الرئيسي هو `main`.
3. أنشأ المستخدم مستودع GitLab: https://gitlab.com/spinel-group/melkit. GitHub هو مصدر التغييرات، ولا نحرر الكود في النسخة المرآة.
4. ملف `.github/workflows/sync-gitlab.yml` يقوم بدفع `main` فقط إلى GitLab، دون بناء Android ودون نسخ APK إلى GitHub. لا يستخدم `--mirror` أو دفعًا قسريًا يحذف عملًا آخر.
   الوجهة الافتراضية مضبوطة في السكربت. تفحص المهمة وجود `GITLAB_TOKEN`؛ إذا غاب تعرض تنويهًا بأن المزامنة معلقة وتتخطى الرفع. بعد إضافة السر يُشغّل workflow يدويًا لأول مزامنة. نجاح فحص الإعداد وحده لا يعني وصول الملفات إلى GitLab.
5. ملف `.gitlab-ci.yml` ينفذ فحص التأسيس الخفيف. بناء Android ينتظر وجود التطبيق وGradle Wrapper وسر التوقيع `MELKIT_SIGNING_BUNDLE` (أو القيم الفردية الأصلية). نجاح فحص التأسيس دون السر لا يعني إنشاء APK.
6. GitLab يبني APK Release بالمفتاح الأصلي؛ يكون تنزيل التجربة من Artifacts. الاحتفاظ الافتراضي 7 أيام مع ضبط احتفاظ آخر pipeline ناجح لتقليل التخزين.
7. AAB يضاف عند طلب بناء النشر عبر `BUILD_AAB=true`؛ لا نبني AAB في كل تجربة.
8. يُزاد `versionCode` لكل APK موزع. القيمة الافتراضية لاحقًا: `MELKIT_VERSION_CODE_BASE + CI_PIPELINE_IID`. لا نعيد ترقيم الإصدارات عند نقل مشروع CI.

| Actions secret | `GITLAB_TOKEN` | اعتماد دفع مخصص للمستودع المقصود فقط؛ لا يوضع في عنوان remote أو السجلات |
| Actions variable اختياري | `GITLAB_REPOSITORY_URL` | تجاوز الوجهة الافتراضية عند الحاجة؛ لا يلزم إضافته للمستودع الحالي |

الوجهة الافتراضية هي الرابط الذي أرسله المستخدم: `https://gitlab.com/spinel-group/melkit.git`. لإكمال الربط، يضيف المستخدم رمز GitLab الذي يستطيع الدفع إلى هذا المشروع باسم `GITLAB_TOKEN` من GitHub → Settings → Secrets and variables → Actions → New repository secret، ثم يُشغّل workflow. لا يُرسل الرمز في الدردشة ولا يوضع في الكود. لا نبني Android داخل GitHub Actions.

### أسرار MelKit — نفس القيم في GitHub وGitLab

لتقليل خطوات النسخ من الهاتف، نجمع بيانات توقيع المفتاح الأصلي في سر واحد. افتح [دليل إعداد التوقيع](docs/SIGNING_SETUP.md) واتبع الخطوات. الحزمة الخاصة سلّمت للمستخدم ولا تدخل مستودع الكود.

| الاسم | الغرض |
| --- | --- |
| `MELKIT_SIGNING_BUNDLE` | السر الأساسي المطلوب: حزمة Base64 تحتوي keystore الأصلي واسم alias وكلمات المرور والبكج؛ نفس القيمة في GitHub وGitLab |
| `MELKIT_GOOGLE_SERVICES_JSON_BASE64` | إعداد Firebase الخاص بـ `com.spinel.melkit`، يضاف في P8 |

للتوافق يبقى دعم المتغيرات الفردية `MELKIT_KEYSTORE_BASE64` و`MELKIT_STORE_PASSWORD` و`MELKIT_KEY_ALIAS` و`MELKIT_KEY_PASSWORD` إذا لم تُستخدم الحزمة. لا يلزم إدخالها عند إعداد `MELKIT_SIGNING_BUNDLE`. المرجع الملزم لبصمة الشهادة هو الملف العام [signing-certificate.sha256](docs/signing-certificate.sha256)، لا قيمة يمكن استبدالها عرضًا في الأسرار.

تستخدم GitLab CI/CD Variables قيَمًا مخفية/مقنّعة حيث يدعم GitLab ذلك، ويضبط نطاق الحماية لفرع البناء الموثوق. حماية المتغير مع فرع غير محمي قد تمنع وصول البناء إليه. نسخة GitHub احتياطية للأسرار وليست سببًا لبناء Android هناك. Base64 ترميز وليس تشفيرًا؛ لا تُنشر قيمه في ملفات المصدر.

## توقيع ثابت من أول بناء

- أنشأ المساعد مفتاح MelKit الأصلي **مرة واحدة** وحفظ نسخة احتياطية خاصة منه قبل توزيع APK. الملف `MelKit-signing-backup.zip` يحتوي الأصل وقيم إعداد البناء؛ لا يُعاد توليده عند تعثر إعداد CI.
- لا يستخدم APK التجربة مفتاح Debug المؤقت. لا نعيد توليد المفتاح عند فشل البناء أو غياب سر.
- `ci/build-android.sh` يرفض البناء عند نقص بيانات التوقيع أو اختلاف البصمة، ولا يحتوي أي توليد مفاتيح.
- تثبيت الإصدار الثاني فوق الأول جزء من قبول P0، مع الحفاظ على بيانات التطبيق.
- لا تُحفظ keystores أو كلمات مرور أو tokens في commit أو artifacts. قواعد `.gitignore` تمنع إدراجها عرضًا.
- عند إعداد Play App Signing نراجع شهادة توقيع التثبيت وشهادة الرفع؛ ثبات مفتاح الرفع وحده لا يضمن تطابق APK المحلي مع APK الذي يوقعه Google Play.

## تكاملات ما قبل الإصدار فقط

### AdMob

يضاف SDK والمعرفات وموافقة UMP قبل الإصدار النهائي بعد استقرار الوظائف. نستخدم معرفات الاختبار أثناء التطوير ونحدد أنواع الإعلانات ومواضعها مع المستخدم في تلك المرحلة. لا نضع إعلانًا يقطع نسخ الملفات أو التحقق أو النقل أو التراجع.

### Firebase والإشعارات

- تم ربط عميل `com.spinel.melkit` من ملف المستخدم في مشروع `scangpapp`. يتتبع المستودع إعداد Android الخاص بهذا العميل وحده؛ لا يلزم سر Firebase إضافي للبناء الحالي. ملف Android العميل ليس اعتماد خادم، ولا يحتوي مفتاح حساب خدمة.
- أضيف استقبال عنوان ونص ورابط تطبيق على Google Play من مفتاح البيانات `url`، مع دعم `link` و`play_url` أو `package_name` للاسم الصالح. تظهر الإشعارات أثناء فتح التطبيق ويُعالج ضغط إشعار Firebase من الخلفية. لا يُفتح الرابط عند مجرد الاستلام.
- يُقبل فقط رابط HTTPS لصفحة تطبيق على المضيف `play.google.com` بمعرّف صالح؛ تُرفض الأهداف الأخرى، وتُزال البيانات بعد معالجتها لمنع الفتح المتكرر. يظهر سؤال النظام للإذن عند أول فتح فقط دون بطاقة خاصة داخل إعدادات MelKit، ولا تطلب المشاركة الإذن مرة أخرى.
- تشمل الاختبارات وصول الإشعار مع التطبيق مفتوحًا وفي الخلفية وبعد إغلاقه، وفتح وجهة المتجر الصحيحة، ورفض رابط غير صالح.
- لا يضاف مفتاح حساب خدمة Firebase أو اعتماد خادم داخل APK.

## English project brief

MelKit (`com.spinel.melkit`) is an Arabic/English Android content manager for Melon Sandbox. It manages existing user content: backup/restore, offline phone-to-phone transfer, exportable bundles, a searchable library, safe mod toggling, activation profiles, duplicate/empty-file checks, supported-format validation, reversible quarantine, local categories, thumbnail preparation, and an operation history.

MMIX remains the general downloaded-file installer. Both original Shizuku tutorial videos and their language-aware internal player are included. On 9 November the user confirmed map/mod/save restoration and use in the game, Shizuku reconnection, and Arabic/English video playback in the corresponding UI languages. Four further changes are prepared on `codex/melkit-ui-review-20261109`: real dashboard totals, the supplied Shizuku Play link, compact file cards/actions, and a numbered-copy restore option for saved-file conflicts. All 369 host checks passed; Android compilation and phone review of these new changes remain deferred at the user's request. In-game category/name and thumbnail changes are experimental until the current formats are verified with real files. No FPS or universal crash-fix promises are made.

GitHub is the source of truth and runs only a short sync workflow. GitLab builds signed release APKs. README must be the first committed file. A permanent signing key must be created once, saved before distribution, and reused for every install-over update. AdMob/UMP and Firebase/FCM with validated Play Store links are late release-preparation work.
